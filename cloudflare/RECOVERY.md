# 更新、备份与恢复

所有线上更新先做备份，再运行 `pnpm cf:migrate`，最后构建部署。升级包含 `0006_uneven_phantom_reporter.sql`，原 JSON 中的业务记录迁入独立表，原账号、机构、截图保持。

## 自动与手动备份

部署模板的 Cron 每天北京时间 03:00 清理超过 24 小时的未关联截图及过期会话，再生成完整数据库备份和已关联截图副本。数据库备份保留 30 天，截图副本持续保留以保障历史恢复。R2 存储桶保持私有，备份含密码散列，按管理员数据保护。

管理员可在系统设置中手动备份并查看结果。只有所有关联截图副本完成后才保存备份 JSON；失败不会产生“完整备份”记录。未启用 Cron 的旧部署不会自动运行，需使用本仓库新版配置部署。

## 恢复演练与事故恢复

1. 从 R2 的 `system-backups/` 下载所需 JSON。不要提交到 GitHub。
2. 新建一个用于恢复的 D1 数据库，运行全部迁移；保持没有任何机构或账号。不要运行 `cf:init`。
3. 执行 `node scripts/restore-backup.mjs backup.json restore.sql`。
4. 将生成的 SQL 导入**新数据库**，导入文件兼容 D1，含空数据库保护，不使用 D1 不支持的显式事务。每条恢复语句都检查本次保护标识；不得移除保护来覆盖生产库。导入中断时保留新库排查或重新建空库恢复，验证前不切换线上绑定。
5. 将备份引用的 `system-backup-images/order-screenshots/<id>` 复制为目标桶的 `order-screenshots/<id>`，或复用原桶（先确认原对象完整）。禁止将私有图片设置为公开访问。
6. 使用临时 Worker/域名绑定恢复数据库和目标桶，验证登录、学员、订单、课表、消课历史及截图。
7. 验证通过后，显式切换生产 Worker 的 D1/R2 绑定并部署。旧库保留用于回退。

本仓库回归测试在隔离 SQLite 中完整恢复备份，并验证非空目标库被拒绝。实际线上恢复需按步骤演练并核对对象文件，不能把本地测试当作线上恢复完成。
